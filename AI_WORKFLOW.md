# AI Workflow Note

## Tools used

**Claude Code** (Sonnet 5), used agentically end-to-end: scaffolding, writing every file, running the dev server, querying the live database, and driving a real headless browser to test the app — not just generating code from a description.

## Where AI materially sped things up

- **Boilerplate that isn't the interesting part of the problem.** Next.js scaffolding, a small shadcn-style UI kit (Button/Dialog/DropdownMenu/etc. built directly on Radix primitives rather than pulling in the full shadcn CLI), Prisma schema + seed data, CRUD route handlers — all of this is well-understood, repetitive work where AI generation is close to free and lets the time budget go toward the product surface (editor feel, sharing UX, import quality) instead.
- **End-to-end verification loop.** Rather than eyeballing code and hoping, the session ran a real Postgres database (Neon), logged in through the actual credentials flow, and drove a headless Chromium browser (Playwright) through every core path — login, create, type/format text, autosave, reload, rename, share, unshare, view-only enforcement, file import (valid and invalid file types), delete-with-confirmation — taking screenshots at each step. That loop caught real bugs (below) that reading the code would not have.
- **Reading the project's own bundled docs before writing framework-specific code.** This app runs Next.js 16 / React 19.2 / Prisma 7, versions newer than the model's training data. Rather than writing route handlers from memory and hoping the API hadn't changed, the session read `node_modules/next/dist/docs` (the project explicitly ships version-matched docs for exactly this reason) before writing any route handler, and confirmed the async `params`/`RouteContext` convention was still correct for this version before relying on it.

## What AI-generated output was changed or rejected

- **Prisma 7 was rejected mid-build.** The initial `npm install` pulled Prisma 7.9.1, which turns out to have replaced schema-file `datasource url` with a driver-adapter config pattern (`prisma.config.ts` + `@prisma/adapter-pg`) that's a genuine breaking change released after the model's training cutoff. Rather than guess at an unfamiliar config API under time pressure, the session pinned down to Prisma 6.19.3 — the last version using the well-understood config shape — and moved on. This is a case of *not* trusting AI-generated code that would have been guessing at an API it didn't actually know.
- **A real autosave bug found via testing, not review.** The editor flushes a pending save via `navigator.sendBeacon` when the tab closes. Playwright testing (typing → reload immediately) surfaced that this beacon was hitting a `405` — `sendBeacon` can only send `POST`, but the API route only accepted `PATCH`. This was invisible from reading the code; it only showed up by actually reloading a real browser against a real save-in-flight. Fixed by aliasing `POST` to the same handler on that route.
- **A test I wrote gave a false-positive bug report, and I didn't take it at face value.** A persistence check did a substring match on saved HTML and reported the edit as "lost." Before concluding there was a data-loss bug, I queried the live database directly for the actual stored JSON — the edit was there; the assertion was just naive about how an italicized selection splits a text node across two marks. Filed as a test bug, not a product bug, and moved on rather than "fixing" working code.
- **Left as-is:** Tailwind flagged some arbitrary-value classes (`text-[var(--muted)]`) as expressible via shorter canonical utilities generated by `@theme inline` (`text-muted`). Cosmetic, not a correctness issue — noted and intentionally not chased given the time budget.

## How correctness, UX, and reliability were verified

1. **Static checks:** `tsc --noEmit` and `eslint` clean; `npm run build` (production build, not just dev) succeeds.
2. **Unit tests:** Vitest covers the two pieces of pure logic worth isolating — access-control role resolution (`resolveRole`/`canEdit`) and the Markdown/text-to-HTML import converters — 16 tests, all passing, no database or browser required.
3. **Real integration testing, not mocks:** every core user flow was driven against a live Neon Postgres instance through the actual NextAuth credentials flow and a real headless browser session (login as three different seeded users, edit and reload to confirm persistence, share/unshare and confirm the permission actually changes what the API returns, upload valid and invalid files, delete with the native confirm dialog). Screenshots were captured and visually reviewed at each step — not just "no console errors," but "does this actually look and feel right."
4. **Test data hygiene:** after using the running app to test destructive flows (delete, import, edit), the seed data was reset back to a clean starting state through the application's own API — not a raw database wipe — so the demo accounts are in a presentable state for review.
